# Pipelines

Built-in pipeline definitions ([ADR-014](../adr/014-pipeline-engine-opt-in-autopilot.md)). The app bundles these files: Rust reads them with `include_str!` (`src-tauri/src/pipelines/`) and the UI imports them (`src/pipeline/defs.ts`). Your own pipelines live in `pipelines.json` in the app data folder and are edited under **Settings › Pipelines**.

## Format

| Field | Meaning |
|---|---|
| `id` | Unique id, also the chain kind on tabs (`eagle1`). Letters, digits, `_` and `-`. |
| `name` | Shown on chain labels ("Eagle-Eye 1 · step 2 of 4"). |
| `runKind` | Optional. The run kind stored on the chain's run; defaults to `id`. Built-ins keep `full` / `execute` so older runs still load. |
| `stages[]` | In order. Each has `id`, `roleId`, `title`. |
| `stages[].kind` | What the stage does: `planner`, `reviewer`, `implementer` or `generic`. Every rule that depends on the role (which HANDOFF sections its reply owes, the plan-mode plan, the send-back ask, fan-out) reads the kind, so a copy of a built-in role (Settings › Roles › Duplicate) works like the original. Left out: from the built-in role id, else `reviewer` for a stage with a `loopBack`, else `generic`. A reviewer whose round goes back to a planner reviews the plan; any other reviews the work. A kind you write must agree with the `loopBack`: a stage with a `loopBack` is a `reviewer`, and a `reviewer` needs a `loopBack`. Otherwise the pipeline is shown disabled with the reason. |
| `stages[].loopBack` | A reviewer stage can send its round back to an earlier stage: `to` (stage id), `maxRounds` (1 to 20; leave it out for no limit, the default: rounds go back until the reviewer approves), `minSeverity` (default `MEDIUM`; findings below it go to follow-ups instead of another round). |
| `stages[].gates[]` | Checks the app runs after the stage's turn, before handing on: `{ "kind": "command", "run": "npm run check" }` (`"auto"` picks `npm run check`, `cargo test`, `npm test`, or `go test ./...` for a folder with `go.mod` at its root, in that order), `{ "kind": "pullRequest" }` (every pull request the stage reported exists on GitHub), and `{ "kind": "verify", "steps": "…" }` (L2: a check the app cannot run itself, such as a Playwright run on a Windows staging build; steps are 1 to 2000 characters). An `auto` command that finds nothing to run stops the run with `no_check_found`; add `"optional": true` to the gate to skip it instead. A `verify` gate waits until the command and pull-request gates have passed, then the run waits with `checkpoint` and the overview shows the steps, the lane and the pull requests it reported, with **Mark verified** and **Failed**. **Mark verified** passes the gate and the run goes on as for a passed check. **Failed** takes a note and sends it back to that stage, resuming its session, as a failed check's output goes back; it counts toward the stage's gate retries, so a gate that keeps failing still stops with `gate_failed`. Each answer is recorded on the run (`verifications`: who, when, verified or failed, the note, the lane, round and attempt) and in the Timeline. While the run waits on a verification, turns other lanes finish are held, not decided; your answer decides them, checks first, so each lane still gets its own verification. A manual **Run checks** skips verify gates: when every check passes, a verification still waiting stays waiting, and when one fails, the wait ends and the run waits for you with the failure. Handing the stage on yourself skips its verification. On an engine-2 run the stage's `submit_result` is checked; the manual hand-off dialog lists missing HANDOFF sections. |
| `stages[].checkpoint` | Autopilot stops before starting this stage and waits for you. |
| `stages[].round` | R1: `true` on a `planner` stage that is a QA round's Triage: it hands over a round (`round.json`) instead of tasks (see below). |
| `stages[].alsoReviewers` | Specialist reviewers (role ids, for example a custom Security Reviewer) that review the same work in parallel with the stage's role. Needs a `loopBack`. A pipeline with parallel reviewers runs on engine 1, which is manual only: you hand the work to each reviewer and send the round back yourself (see below). |
| `approveAtEnd` | R1: when the last stage approves, the run waits for you (`checkpoint`) instead of completing; **Approve round** completes it. The QA round sets it. |
| `autopilot.pauseAtUsagePercent` | Autopilot pauses when the Claude 5-hour or 7-day usage reaches this percent (default 90). |
| `autopilot.stallMinutes` | While a stage is Working, this many minutes with no terminal output and no growth of its session log stops the run with `stalled` (default 30, 1 to 1440). Raise it for a pipeline whose checks run quietly for long. |

Every role id must exist. When the app loads your pipelines (and whenever a role is added or deleted), one that does not validate stays listed under Settings › Pipelines, **disabled**, with the reason; it is never dropped, and an entry that is not a pipeline at all is kept exactly as written. A disabled pipeline cannot be started, and autopilot stops a run whose pipeline became disabled or unknown instead of guessing one.

## Engine 2 and the run actor

A new run gets engine 2 when every stage of its pipeline reports through the pipeline bridge, told apart by the stage's kind (so a copied role counts like its original): a `planner` stage, a `reviewer` stage with no `alsoReviewers`, and an `implementer` stage. Eagle-Eye 1 and 2 qualify. Only engine-2 runs have autopilot.

**Engine-1 runs are manual only.** A run saved before pipeline v2, and a new run of any other pipeline (a stage with `alsoReviewers`, or a `generic` stage), runs on engine 1. Its autopilot switch is off and cannot be turned on, and the chain overview says why; a run saved with autopilot on keeps going by hand. Every hand-off waits for you: **Send to …**, **Send back to …**, **Run checks** and **Mark approved** work as before, and the overview still draws each stage's turns, verdicts and checks. The app reads an engine-1 stage's verdict and HANDOFF sections from its reply (the regex parsers in `src/handoff/`) only to show them and to fill the next form; nothing decides or types on such a run. The frontend autopilot that used to drive engine-1 runs (ADR-014 §5, its hand-off claims, and Continue after a restart) was removed in pipeline v2 V6.

On an engine-2 run, one Rust **run actor** per run is the only thing that acts on it (`src-tauri/src/run_actor/`). It hears each stage's finished turn from the bridge, runs the stage's gates on a thread of its own, decides, and carries the decision out: it opens the next stage's terminal with a prompt built from the role template and the run folder (`plan.md`, `prs.json`, `tasks.json`; the prompt also points at those files), sends a round back or a failed check's output to the stage that must act, and starts lanes that were waiting. Sending back stops that stage's `claude` (SIGTERM, then SIGKILL after 10 s) and resumes its session in the same terminal (`claude --resume`, same flags) with a short prompt: a review round's points at `findings-<stage>-r<N>.json` in the run folder, a failed check's carries its output. The tab you watch stays and shows the resumed session. Your Send on such a run fills the next stage's form from the run folder's files, and you can still edit it. Your **Send**, **Send back**, **Approve** and **Continue** on such a run are messages to the same actor, handled one at a time with autopilot's own steps, so the two never make the same hand-off twice. If the actor fails, the run stops (`stopped`, reason `carry_out_failed`) and the stage terminals keep running for you to finish by hand.

### Tickets from ClickUp (intake)

When you tick Eagle-Eye on the start screen and the window's Claude account has ClickUp set up (**Settings › Integrations**), a **Tickets from ClickUp** box takes task links, list links and task ids. **Fetch** reads them with that account's token and workspace only and shows the tickets the run would take, with a checkbox each, and the ones it leaves out: closed and done tickets, and any your filters drop, each with the reason. The filters are priority, status (by name, any case) and tags (a ticket with any ticked tag stays); after a Fetch the box offers the statuses and tags it saw. One intake takes at most 100 tickets; past that, Fetch says how many matched and still offers the statuses and tags it saw, and Start waits until a Fetch is under the cap. Each ticket's full read at Start is filtered again, so one closed or changed since Fetch is excluded with its reason. A task with subtasks counts as an epic, so its subtasks are the tickets. Links can be pasted bare or as Markdown (`[text](url)`) or Slack (`<url|text>`) links. **Start** reads each ticked ticket again in full (its Markdown description and tags) with its comments and writes them into the run folder as `tickets.json` (`schema: 1`; descriptions and comments are capped and the file says so; it never holds the token). The first stage's context names the file and lists one line per ticket; later stages see it in the run's hand-off files. The task text you type or dictate is unchanged. A start that does not begin an engine-2 run gets the same summary in its request instead, and no file.

The snapshot does not change by itself. The chain overview says how many tickets ClickUp edited since intake (it checks at most every 5 minutes), and **Pull again** re-reads them into `tickets.json` and adds a Timeline note. Running stages are not prompted again.

### ClickUp updates (write-back)

Once a lane's `verify` gate is marked verified, or the run completes, the chain overview shows **ClickUp updates**: one row per ticket in `tickets.json`. Each row proposes a comment (the lane's pull requests, the Implementer's summary of what changed, and how it was verified: the verify steps and your note, or "Checks passed: …" when there was no verify gate) and, only for a ticket whose lane was marked verified, a status change to the status you mapped for its list. A ticket's lane comes from the plan's tasks when they name tickets (`tasks[].tickets`, or the tickets of a task's stories); otherwise a run with one lane (or none) gives every ticket to it, and a run with several lanes proposes no status and says why.

Map each list's "verified" status once (for example `QA PASSED`), from the list's real statuses, next to the updates or under **Settings › Integrations** (kept per Claude account and list in `settings.json`). A row has a tick (off until you tick it), its comment to edit, a status picker with the list's statuses (or no status change), and **Skip**. **Send ticked** posts only the ticked rows, with the Claude account and workspace the tickets were taken with; it refuses in a window of another account, or when that account's workspace changed since intake. Your ticks are kept in the app's memory, not trusted from the file: a stage can write the run folder, so a tick in `writeback.json` counts only when you gave it in this app session with that exact comment and status. **Ticks do not survive a restart** (on purpose): after one, tick again. Send carries each ticked row as you saw it, and a row goes only if your tick, `writeback.json` and the row you saw all agree and its ticket is in `tickets.json`; a row that changed meanwhile is reported as "changed since you ticked it" and not sent, and a tick or row written straight into the file never sends anything. A rebuild (a lane verified later, a list mapped) unticks any row whose comment or status it changes. Each step is saved before the next call: the status once set, then, just before the comment is posted, a mark that it may be posted. A comment whose POST did not finish cleanly (the app quit or crashed mid-call, ClickUp timed out, the connection was reset or broke while the answer was read, or ClickUp answered with a server error or an unexpected status) keeps that mark, so sending it again asks you to check the ticket and confirm. Only a failure before anything was sent counts as not posted: the name did not resolve, or the connection was never made (refused, unreachable, timed out while connecting, or a proxy or TLS setup that failed), as when you are offline; so does ClickUp refusing the comment. Once ClickUp's status line has arrived, it is the answer even if the rest is lost: success means posted, a refusal means not posted, and a server error stays maybe posted. The app remembers the mark as soon as it sees it, so a file that clears it later does not skip the question; only your confirmed resend does. Results are kept in `writeback.json` (`schema: 1`; never a token) and noted on the Timeline, also when a save fails (sending then stops): sent, with the time, or failed, with ClickUp's error in plain English (a status set before a failed comment is recorded). A row whose comment ClickUp refused stays ticked to retry. A sent row cannot be sent again until you edit its comment or status, and only what changed is sent. When a later verification makes a sent ticket newly verified, or (unless you picked its status yourself) adds its mapped status, the row becomes an unticked follow-up with a short comment naming what was verified; it keeps your own status choice and your skip. A verification answered again, or a later failure, makes no follow-up. Built comments are cut to ClickUp's 10,000-character limit and say so. A ticket the plan does not tie to a lane gets a note listing the run's pull requests, with no claim that it was verified. The app writes nothing else to ClickUp: no new tickets, no deletes, no assignees, no descriptions.

### Hidden stages, Watch and Take over

Stage terminals the run actor opens start **hidden**: they run at 120×40 with nothing drawing them, and the app keeps the newest 2 MB of each one's output. Opening the stage's tab, **Watch in split** on the overview, or a grid cell **watches** it: the view replays that output, then goes live, and the terminal is resized to the view once so Claude Code redraws its screen cleanly. When the last view of a stage leaves the screen, the app lets go of it again; closing a view never stops a stage.

While autopilot drives a stage its view is **read-only**, so you and autopilot never type into it at once. You can type while the stage **needs you** (a permission dialog, a question) and while you have **taken it over**; the backend refuses keystrokes at any other time, and so does the view. A run with autopilot off has no read-only stages.

**Take over** (on the overview or on the view's bar) hands a stage to you: its bridge stops asking for a result at the end of a turn, autopilot no longer decides its turns, a stall or an exit there does not stop the run, and its view takes keystrokes. When that stage was all the run was waiting on, the run waits with reason `taken_over`. A decision that would act on a stage you took over (a reviewer's round sent back to it) waits the same way, and Hand back carries it out. While the run waits like this, turns the other stages (or lanes) finish stay undecided, and Hand back decides them too. If you revised the stage yourself after that round's turn, the round is recorded as dealt with by you and not sent. A run that goes to engine 1 mid-run releases every stage you took over, since a manual run is yours throughout. **Hand back** turns enforcement and decisions on again; if the stage's current turn already has a result, autopilot decides on it at once, otherwise it waits for the next turn.

A pipeline with an `implementer` stage can **fan out** at that stage: the stage before it (its plan) lists several pull requests, and each gets its own lane of the remaining stages in its own git worktree. See `docs/PIPELINE-REPLY-GUIDE.md`. On an engine-2 run whose Planner launched with the bridge, fan-out reads the Planner's tasks from the run folder's `tasks.json` instead of the reply's list.

A plan can span repos (L1). **Settings › Repos** names your git repos (`backend` → its folder); the Planner's prompt lists them, and a task can set `"repo": "engine"`. Fan-out then makes that lane's worktree in the repo's folder, on the usual lane branch (`<runId>-pr2`); a task without `repo` uses the run's own folder. The lane's terminal, its checks and its PR Reviewer all run in that worktree, and the overview labels the lane with its repo (`PR2 — Client · engine`). `dependsOn` works across repos as it does within one, so "backend before its clients" is a plain dependency. The bridge checks each `repo` against the names the app wrote into the run folder (`repos.json`) and names the valid ones when it rejects one. A repo removed from Settings after the plan was accepted is never replaced by another folder: fan-out refuses it, and the run actor stops the run with `carry_out_failed` before it starts a lane there.

A repo in **Settings › Repos** can also carry a **check** and **verify steps** (L2). The check is one command line of at most 2000 characters (`backend` → `cd server && go test ./...`, `engine` → `go test ./...`). In a lane made in that repo it replaces the stage's `command` gates, at the first one's place and with its `timeoutSecs`, and runs in the lane's worktree with the same timeout and process-tree rules; the stage's `pullRequest` and `verify` gates still apply. The overview and Timeline name it (`backend check: cd server && go test ./...`). The verify steps (at most 2000 characters, several lines allowed) join that stage's gates as one more `verify` gate, labelled `backend verify`, so the run waits for you once the check passes. Both apply only to the lane's stages that have a `command` gate (the Implementer in Eagle-Eye), never to a reviewer, and not to stages outside a lane or lanes with no repo. A repo with neither keeps the pipeline's gates exactly as written.

### Stories inside a pull request (L3)

A plan ships one pull request per repo (decision E7), and a task can build that pull request in **stories**. The Planner may add `stories` to a task, especially when the run has a `tickets.json`: 1 to 20, each with an `id` (`s1`, unique in the task), a `title`, and optionally `tickets` (ids or custom ids from `tickets.json`, checked against it when the run has one), `doneWhen` and `plannedTests` (short lines), and `checkpoint`: what you do and report before the next story (Plan 5's R5 instrumentation: rerun on Windows and read the log). A manual task has no stories, and the last story has no checkpoint. The bridge names every problem at once, as for the tasks. A task without `stories` runs exactly as before.

The task's Implementer (a lane's, or the run's own when the plan has one task and does not fan out) works through the stories in order, in **one Claude session on one branch**. Its first prompt lists every story, then asks for `s1`. After each story it calls `submit_result` with `story` set and a `summary`; `prs` may be `[]` until the last story, which reports the draft pull request as usual. The bridge takes a result for the current story only (the stage folder's `story.json`, which the app keeps current) and names the current story when it refuses one.

After each story the lane's command checks run: the repo's check (L2), else the stage's `command` gates. The `pullRequest` and `verify` gates run only after the last story. A pass resumes the same session with the next story (`Story 2 of 4: …`); a failure sends the output back for the same story under the usual retry rule and limit. A checkpoint story's checks passing makes the run wait with `checkpoint`: the overview shows the story's checkpoint text, a note box and an optional box of stories to add (one per line, added right after it), and **Continue** resumes the session with the next story and your note. While a checkpoint story waits, the turns other lanes finish are held for your Continue, as for a verify wait; a story turn that ends during another lane's verify wait is held the same way. After the last story the pull request goes on as before: its pull-request and verify gates, then the PR Reviewer, whose loop-back resumes the Implementer for the round without restarting the stories; a review round reports the pull request, never an empty list, and a story's result with no pull request leaves `prs.json` as it was. A wait for your answer (a checkpoint story's, or a verify gate's) survives turning autopilot off and on, with its held turns: turned on again, the run waits on it as before, and only your Continue or answer, your own hand-on, Send back, Approve, or a different stop ends it. While autopilot is off, Continue and Resend story are refused. The last story waiting on its verify gate is `verifying` and shows only the Verify panel. When the run stops mid-loop (a story's checks failed too often, a usage pause, a turn that named no story), **Resend story** in the overview sends the current story to the same session again, with its retries started over; turning autopilot on again runs such a run, as for any stop, so a story whose checks failed can still be resent once nothing else is under way for it. When a wait ends without your answer (another stop, your hand-on, an approval in another lane), its story is active again, so Resend story picks it up. A failed **Run checks** ends a verify wait even while autopilot is off. While autopilot is off, the turns stages finish are recorded but neither held nor decided. Handing the pull request on past the Implementer (your Send, a Chat tab or a startup form joining the chain with the hand-off), or approving it, with stories not finished marks them `skipped` with a Timeline line, so a later review round is never taken for a story; a hand-on you record and then release skips nothing. Your **Run checks** before the last story runs the command checks only, as autopilot does.

One session per lane is the rule (decided in L3): there is no option to start a story in a fresh session for now. Each story's summary stays on the run, so such a split can be added later.

The run records one entry per story (`stories`: the lane, the task, the story's fields, its status — pending, active, checks running, checks failed with the attempt, waiting on you, waiting on your verification, done, skipped — the turn that reported it, its summary and your note), so C3 can read each story's summary and tickets. The chain overview labels the lane with its progress (`PR1 — Engine fixes · engine · story 2/4`) and lists the stories under it; a run with no lanes lists them under **Stories**.

### QA rounds: Triage (R1)

A QA round starts with **Triage**: tick **QA round** on the start screen with the Triage role (and, when the window's account has ClickUp set up, the tickets in **Tickets from ClickUp**), or paste the tickets you dictated, or your own round plan, into its form. The built-in pipeline **QA round** (`docs/pipelines/round.json`, engine 2) is Triage → Plan Reviewer (its rounds go back to Triage) → your approval.

Triage (`docs/roles/role-triage.md`, role `role_triage`) is a `planner` stage marked `"round": true`, so it runs in plan mode and reports through ExitPlanMode, as the Planner does. It reads `tickets.json` (or your text) and the repos of Settings › Repos (`repos.json`), confirms each ticket against the code and corrects claims that turn out wrong, groups the tickets into plans by shared contract, orders the plans into merge waves by shared repos and files, and marks a plan `deferred` (its fix is outside our repos) or `parked` (it waits on a product decision), with a reason. Its plan is the round document, with the sections of a QA fix-plan doc (summary, plan overview, priority and merge order, plan detail, deferred and parked plans, excluded tickets, open questions), and ends with a fenced ```json block holding `round` (`schema: 1`):

| Field | Meaning |
|---|---|
| `plans[]` | 1 to 30. `id` (`plan1`, …, unique), `title`, `tickets[]` (ids or custom ids from `tickets.json`), `repos[]` (names from Settings › Repos; empty for the run's own folder), `status` (`active`, `deferred`, `parked`), `reason` (required for deferred and parked), `wave` (required for active plans; deferred and parked plans may have none), `summary`. |
| `waves[]` | `n` (1, 2, … with no gap; each wave has a plan) and `why`. |
| `mergeOrder` | `{ repo: [planId, …] }`: the order each repo's pull requests merge in. |
| `excluded[]` | `{ ticket, reason }`: tickets left out of every plan. |

The hook checks the block and names every problem at once, so Triage fixes them and calls ExitPlanMode again: every ticket of `tickets.json` is in exactly one plan or in `excluded` (a dictated round's ticket names are not checked); an active or parked plan's repos are names from `repos.json` (a deferred plan's are only listed, since its fix is elsewhere); every active plan has a wave; `mergeOrder` names only plans that touch that repo, never a deferred plan, and lists every active plan of each repo it touches; in each repo a later wave's plan never merges before an earlier wave's, and the order across repos never goes round in a circle; ids are unique. A round that passes is written as `round.md` (the plan text) and `round.json` at the run folder's top, and Triage hears "Plan received". A round run writes no `tasks.json`; a pipeline with a round stage has no implementer stage.

The Plan Reviewer gets the round document as the plan, a note on what to check in a round, and `round.md` and `round.json` among the run's hand-off files. A pipeline with `"approveAtEnd": true` never completes by itself: when its last stage approves, the run waits with `checkpoint`, and **Approve round** (the overview's Mark complete) completes it. The chain overview shows **Round** for a run with a `round.json`: a table of the plans with their tickets, repos, wave and status (and why a plan is deferred or parked), the waves, each repo's merge order, the excluded tickets, and the round document. A Triage run proposes no ClickUp updates; each plan's own run does.
