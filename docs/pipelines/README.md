# Pipelines

Built-in pipeline definitions ([ADR-014](../adr/014-pipeline-engine-opt-in-autopilot.md)). The app bundles these files: Rust reads them with `include_str!` (`src-tauri/src/pipelines/`) and the UI imports them (`src/pipeline/defs.ts`). Your own pipelines live in `pipelines.json` in the app data folder and are edited under **Settings › Pipelines**.

## Format

| Field | Meaning |
|---|---|
| `id` | Unique id, also the chain kind on tabs (`eagle1`). Letters, digits, `_` and `-`. |
| `name` | Shown on chain labels ("Eagle-Eye 1 · step 2 of 4"). |
| `runKind` | Optional. The run kind stored on the chain's run; defaults to `id`. Built-ins keep `full` / `execute` so older runs still load. |
| `stages[]` | In order. Each has `id`, `roleId`, `title`. |
| `stages[].kind` | What the stage does: `planner`, `reviewer`, `implementer` or `generic`. Every rule that depends on the role (which HANDOFF sections its reply owes, the plan-mode plan, the send-back ask, fan-out) reads the kind, so a copy of a built-in role (Settings › Roles › Duplicate) works like the original. Left out: from the built-in role id, else `reviewer` for a stage with a `loopBack`, else `generic`. A reviewer whose round goes back to a planner reviews the plan; any other reviews the work. A kind you write must agree with the `loopBack`: a stage with a `loopBack` is a `reviewer`, and a `reviewer` needs a `loopBack`. Otherwise the pipeline is shown disabled with the reason. |
| `stages[].loopBack` | A reviewer stage can send its round back to an earlier stage: `to` (stage id), `maxRounds` (1 to 20; leave it out for no limit, the default: rounds go back until the reviewer approves), `minSeverity` (default `MEDIUM`; findings below it go to follow-ups instead of another round). |
| `stages[].gates[]` | Checks the app runs after the stage's turn, before handing on: `{ "kind": "command", "run": "npm run check" }` (`"auto"` picks `npm run check`, `cargo test`, or `npm test` from the folder), `{ "kind": "pullRequest" }` (every pull request the stage reported exists on GitHub). An `auto` command that finds nothing to run stops the run with `no_check_found`; add `"optional": true` to the gate to skip it instead. On an engine-2 run the stage's `submit_result` is checked; the manual hand-off dialog lists missing HANDOFF sections. |
| `stages[].checkpoint` | Autopilot stops before starting this stage and waits for you. |
| `stages[].alsoReviewers` | Specialist reviewers (role ids, for example a custom Security Reviewer) that review the same work in parallel with the stage's role. Needs a `loopBack`. A pipeline with parallel reviewers runs on engine 1, which is manual only: you hand the work to each reviewer and send the round back yourself (see below). |
| `autopilot.pauseAtUsagePercent` | Autopilot pauses when the Claude 5-hour or 7-day usage reaches this percent (default 90). |
| `autopilot.stallMinutes` | While a stage is Working, this many minutes with no terminal output and no growth of its session log stops the run with `stalled` (default 30, 1 to 1440). Raise it for a pipeline whose checks run quietly for long. |

Every role id must exist. When the app loads your pipelines (and whenever a role is added or deleted), one that does not validate stays listed under Settings › Pipelines, **disabled**, with the reason; it is never dropped, and an entry that is not a pipeline at all is kept exactly as written. A disabled pipeline cannot be started, and autopilot stops a run whose pipeline became disabled or unknown instead of guessing one.

## Engine 2 and the run actor

A new run gets engine 2 when every stage of its pipeline reports through the pipeline bridge, told apart by the stage's kind (so a copied role counts like its original): a `planner` stage, a `reviewer` stage with no `alsoReviewers`, and an `implementer` stage. Eagle-Eye 1 and 2 qualify. Only engine-2 runs have autopilot.

**Engine-1 runs are manual only.** A run saved before pipeline v2, and a new run of any other pipeline (a stage with `alsoReviewers`, or a `generic` stage), runs on engine 1. Its autopilot switch is off and cannot be turned on, and the chain overview says why; a run saved with autopilot on keeps going by hand. Every hand-off waits for you: **Send to …**, **Send back to …**, **Run checks** and **Mark approved** work as before, and the overview still draws each stage's turns, verdicts and checks. The app reads an engine-1 stage's verdict and HANDOFF sections from its reply (the regex parsers in `src/handoff/`) only to show them and to fill the next form; nothing decides or types on such a run. The frontend autopilot that used to drive engine-1 runs (ADR-014 §5, its hand-off claims, and Continue after a restart) was removed in pipeline v2 V6.

On an engine-2 run, one Rust **run actor** per run is the only thing that acts on it (`src-tauri/src/run_actor/`). It hears each stage's finished turn from the bridge, runs the stage's gates on a thread of its own, decides, and carries the decision out: it opens the next stage's terminal with a prompt built from the role template and the run folder (`plan.md`, `prs.json`, `tasks.json`; the prompt also points at those files), sends a round back or a failed check's output to the stage that must act, and starts lanes that were waiting. Sending back stops that stage's `claude` (SIGTERM, then SIGKILL after 10 s) and resumes its session in the same terminal (`claude --resume`, same flags) with a short prompt: a review round's points at `findings-<stage>-r<N>.json` in the run folder, a failed check's carries its output. The tab you watch stays and shows the resumed session. Your Send on such a run fills the next stage's form from the run folder's files, and you can still edit it. Your **Send**, **Send back**, **Approve** and **Continue** on such a run are messages to the same actor, handled one at a time with autopilot's own steps, so the two never make the same hand-off twice. If the actor fails, the run stops (`stopped`, reason `carry_out_failed`) and the stage terminals keep running for you to finish by hand.

### Tickets from ClickUp (intake)

When you tick Eagle-Eye on the start screen and the window's Claude account has ClickUp set up (**Settings › Integrations**), a **Tickets from ClickUp** box takes task links, list links and task ids. **Fetch** reads them with that account's token and workspace only and shows the tickets the run would take, with a checkbox each, and the ones it leaves out: closed and done tickets, and any your priority filter drops, each with the reason. A task with subtasks counts as an epic, so its subtasks are the tickets. **Start** reads the ticked tickets again with their comments and writes them into the run folder as `tickets.json` (`schema: 1`; descriptions and comments are capped and the file says so; it never holds the token). The first stage's context names the file and lists one line per ticket; later stages see it in the run's hand-off files. The task text you type or dictate is unchanged. A start that does not begin an engine-2 run gets the same summary in its request instead, and no file.

The snapshot does not change by itself. The chain overview says how many tickets ClickUp edited since intake (it checks at most every 5 minutes), and **Pull again** re-reads them into `tickets.json` and adds a Timeline note. Running stages are not prompted again.

### Hidden stages, Watch and Take over

Stage terminals the run actor opens start **hidden**: they run at 120×40 with nothing drawing them, and the app keeps the newest 2 MB of each one's output. Opening the stage's tab, **Watch in split** on the overview, or a grid cell **watches** it: the view replays that output, then goes live, and the terminal is resized to the view once so Claude Code redraws its screen cleanly. When the last view of a stage leaves the screen, the app lets go of it again; closing a view never stops a stage.

While autopilot drives a stage its view is **read-only**, so you and autopilot never type into it at once. You can type while the stage **needs you** (a permission dialog, a question) and while you have **taken it over**; the backend refuses keystrokes at any other time, and so does the view. A run with autopilot off has no read-only stages.

**Take over** (on the overview or on the view's bar) hands a stage to you: its bridge stops asking for a result at the end of a turn, autopilot no longer decides its turns, a stall or an exit there does not stop the run, and its view takes keystrokes. When that stage was all the run was waiting on, the run waits with reason `taken_over`. A decision that would act on a stage you took over (a reviewer's round sent back to it) waits the same way, and Hand back carries it out. While the run waits like this, turns the other stages (or lanes) finish stay undecided, and Hand back decides them too. If you revised the stage yourself after that round's turn, the round is recorded as dealt with by you and not sent. A run that goes to engine 1 mid-run releases every stage you took over, since a manual run is yours throughout. **Hand back** turns enforcement and decisions on again; if the stage's current turn already has a result, autopilot decides on it at once, otherwise it waits for the next turn.

A pipeline with an `implementer` stage can **fan out** at that stage: the stage before it (its plan) lists several pull requests, and each gets its own lane of the remaining stages in its own git worktree. See `docs/PIPELINE-REPLY-GUIDE.md`. On an engine-2 run whose Planner launched with the bridge, fan-out reads the Planner's tasks from the run folder's `tasks.json` instead of the reply's list.
